Jobs, stages, tasks y waves

Fuentes: Apache Spark · Cluster overview (glosario), Apache Spark · Web UI, Databricks · Look at longest stage, Databricks · Compute configuration y la guía de optimización (Cluster usage).

Qué problema resuelveEntender por qué el cluster no va más rápido

Subes de 8 a 16 workers y el job tarda lo mismo. O cambias shuffle.partitions de 200 a 201 y un stage tarda casi el doble. Las dos cosas se explican con la misma cuenta: cuántas tasks tiene el stage frente a cuántos cores hay para ejecutarlas.

Definiciones cortasDe lo grande a lo pequeño

TérminoQué esLo crea
JobUn cálculo paralelo hecho de muchas tasks, que se lanza en respuesta a una acción (write, count, collect…)Cada acción
StageUn grupo de tasks dentro de un job. Los stages dependen unos de otros, como las fases map y reduce de MapReduceCada shuffle (Exchange) corta un stage nuevo
TaskUna unidad de trabajo que se envía a un executor. Procesa una particiónUna por partición del stage
ExecutorProceso en un worker que ejecuta tasks en varios hilos y guarda datos en memoria o disco. Databricks corre un executor por workerEl cluster
Core / slotUn hueco donde corre una task a la vez (por defecto, 1 task = 1 core)Los cores de los workers
WaveUna ronda de tasks que corren a la vez. No es un término oficial ni una config: es el resultado de dividir tasks entre cores. La guía de Databricks lo llama iterationstasks ÷ cores

Idea mentalUna cocina con turnos

Un pedido grande (el job) pasa por estaciones (los stages): primero todo se corta, luego todo se cocina. La estación de cocina no puede empezar hasta que se haya cortado todo, porque cada olla necesita ingredientes de todas las tablas de corte. Ese paso de una estación a otra es el shuffle. Cada estación tiene una pila de platos que preparar (las tasks) y un número fijo de cocineros (los cores). Si hay 20 platos y 8 cocineros, se trabaja en 3 turnos (las waves): 8, 8 y 4. En el último turno, 4 cocineros miran.

Cómo funciona por dentroDe la acción a las waves

    
    
      
  1. La acción crea el job. Mientras solo encadenas transformaciones no pasa nada. Al llamar a write, count o collect, el driver crea un job.
    2. 
      
  2. El plan se corta en cada Exchange. Todo lo que va seguido sin shuffle (scan, filter, select, agregación parcial) cabe en un mismo stage, y Spark lo fusiona en un bloque WholeStageCodegen. Cada Exchange obliga a terminar un stage y empezar otro.
    3. 
      
  3. Cada stage tiene una task por partición. El primer stage tiene tantas tasks como trozos de entrada (~128 MB cada uno). Los stages que leen un shuffle tienen tantas como spark.sql.shuffle.partitions, o menos si AQE une particiones.
    4. 
      
  4. El scheduler reparte tasks en cores libres. Cuando un core queda libre, recibe la siguiente task pendiente. Con 64 cores corren 64 tasks a la vez como máximo.
    5. 
      
  5. Un stage espera al anterior. El stage que lee un shuffle necesita los bloques de todas las map tasks, así que no empieza hasta que el stage anterior termina. Dos stages independientes, como los dos lados de un join, sí pueden correr a la vez.
    6. 
      
  6. Las waves salen solas de la cuenta. waves = ⌈tasks ÷ cores⌉. Si las tasks duran parecido, el stage tarda más o menos waves × duración de una task.
    7.

Cómo se usaEjemplo que puedes correr


df  = spark.range(0, 50_000_000, numPartitions=40)
agg = df.groupBy((df.id % 1000).alias("k")).count()

agg.explain()   # cada Exchange del plan es una frontera de stage
agg.count()     # la acción: aquí se lanza el job

    
En el plan verás HashAggregate (parcial), Exchange hashpartitioning(k, …) y otro HashAggregate (final). Son dos stages: el primero con 40 tasks y el segundo con las particiones del shuffle (o menos, si AQE las une).

    
En serverless (Free Edition) no eliges los cores ni ves el Spark UI, así que las waves no se observan directamente. Para verlas necesitas un cluster clásico: Spark UI → stage → Event Timeline, que muestra las tasks en el tiempo por executor. En el query profile de serverless solo verás los operadores y sus tiempos; verifica qué detalle por task ofrece en tu workspace.


    
Cuándo usar esta cuentaReglas de la doc

    
    
      
  • Un stage con 1 sola task puede ser señal de problema (Databricks, Look at longest stage).
    • 
      
  • Menos tasks que cores antes de una UDF lenta: haz repartition() para usar todos los cores (Databricks, slow stage low I/O).
    • 
      
  • Shuffle partitions múltiplo de los cores totales de los workers, para que ningún core quede ocioso en ninguna iteración. Sin ajuste fino, entre 2 y 3 veces los cores (guía de optimización).
    • 
    


    
Con qué se confunde

    
    
      
  • Stage vs operación. Un stage no es una operación. Agrupa todas las operaciones narrow seguidas hasta el siguiente shuffle.
    • 
      
  • Job vs acción. En principio, una acción da un job. Con AQE y broadcast es normal ver varios jobs por una sola acción, porque cada query stage se lanza aparte.
    • 
      
  • Task vs partición. Es una relación 1:1 dentro de un stage. Cambiar las particiones es cambiar las tasks.
    • 
      
  • Workers vs executors vs cores. En Databricks hay 1 executor por worker. Los slots para tasks son los cores de esos executors. Lo que cuenta para las waves son los cores totales, no los workers.
    • 
      
  • Skipped stages. En el Spark UI aparecen como skipped cuando el shuffle que producían ya estaba escrito y se reutiliza. No es un error.
    • 
      
  • Waves y skew. Con skew, una task dura mucho más que las demás. El problema no son las waves sino esa task. Más cores no la parten.
    • 
    


    
Qué pasaría si

    
    
      
  • Duplicas los workers con 200 tasks y pasas de 128 a 256 cores: el stage pasa de 2 waves a 1, pero 56 cores no tienen nada que hacer. Pagas más y ganas menos de lo que esperabas.
    • 
      
  • Pones shuffle.partitions = cores + 1: casi duplicas el tiempo del stage por una sola task.
    • 
      
  • Usas auto: Databricks elige el número de particiones según el plan y el tamaño de la entrada. Es la recomendación para shuffle alto.
