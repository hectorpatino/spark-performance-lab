Leer el query profile para encontrar el cuello de botella

Fuentes: Query profile Azure · Query performance insights Azure · Serverless notebooks: query insights Azure · Photon Azure · Query history system table Azure

Lo esencial en 1 minuto

  • En serverless y en SQL warehouses no hay Spark UI. El query profile muestra la ejecución por operadores (Scan, Join, Shuffle, Aggregate), no por stages ni tasks.
  • Ábrelo desde Query History, desde el SQL editor o con See performance debajo de la celda, y luego See query profile. Necesitas ser el dueño de la query o tener CAN MONITOR sobre el warehouse.
  • Cambia la métrica del DAG entre Time spent, Memory peak y Rows, o abre Top operators, y mira qué operador está arriba.
  • Tres lecturas del examen. Scan dominante con poco pruning: mal data skipping. Join con muchas más filas de salida que de entrada, o dos Shuffle grandes con un lado pequeño: join ineficiente. Shuffle con spill en Memory peak: shuffle y spill.
  • Para buscar las mismas señales en todas las queries, usa system.query.history (pruned_files, spilled_local_bytes, shuffle_read_bytes).

Si solo recuerdas una cosa: que el Scan sea caro es normal; mira el porcentaje de pruning antes de concluir que hay un problema.

Qué problema resuelveEn serverless no hay Spark UI

Sin Spark UI, el query profile es la vista con la que encuentras el cuello de botella.

En un notebook o un job serverless, y en un SQL warehouse, no tienes la pestaña de stages ni la de tasks. La doc de serverless lo dice sin rodeos: el acceso al Spark UI no está disponible. Lo que tienes es el query profile, que muestra la ejecución por operadores (Scan, Join, Shuffle, Aggregate) en vez de por stages y tasks.

El examen lo pide de forma literal. En la sección 6: usar el query profile para analizar la query e identificar cuellos de botella, como mal data skipping, tipos de join ineficientes y shuffle de datos. En la sección 5: usar el Query Profiler UI y el Spark UI para monitorear cargas. Y en la sección 9 aparece entre las fuentes de información de diagnóstico, junto al Spark UI, los logs del cluster y las system tables. Esta página entrena las tres lecturas de la sección 6.

Definición cortaQué es

El query profile es la vista de una ejecución concreta de una query: un grafo dirigido (DAG) de operadores con sus métricas (tiempo, memoria, filas), un panel de resumen con la duración y el I/O, y los performance insights que Databricks detectó. Sirve para ver de un vistazo la parte más lenta y para descubrir errores comunes, como joins que explotan o lecturas de tabla completa.

Idea mentalEl parte de una cadena de montaje

Piensa en una planta con estaciones en fila: recepción de material, control de calidad, traslado entre naves, ensamblaje, empaque. Al final del turno cada estación entrega su parte: cuántas horas-persona gastó, cuánto espacio de bodega ocupó como máximo y cuántas piezas pasó a la siguiente. El query profile es ese parte. Tiempo es Time spent, bodega es Memory peak y piezas es Rows.

Con el parte en la mano no adivinas. Si recepción gastó el 86% de las horas descargando camiones enteros para usar tres cajas, revisa el pedido antes de acelerar el ensamblaje. Si ensamblaje recibió 20 millones de piezas y entregó 3,100 millones, algo está duplicando. Si la bodega del ensamblaje se desbordó y hubo que llevar cajas al patio (spill), te falta espacio o te sobran cajas.

Cómo abrirloTres caminos y un requisito

Llegas siempre a un panel de detalles y de ahí a See query profile.

  1. Desde Query History. En la barra lateral, Query History. Haz clic en el nombre de una query: se abre a la derecha el panel de detalles de la query (el resumen). Ahí pulsa See query profile para abrir el DAG completo. Puedes filtrar la lista por usuario, fechas, compute, duración, estado, tipo de sentencia, statement ID y query tags.
  2. Desde el SQL editor o un warehouse. Durante y después de la ejecución aparece abajo un enlace con el tiempo transcurrido y las filas devueltas. Ese enlace abre el panel de detalles, y de ahí See query profile.
  3. Desde un notebook serverless (o en un SQL warehouse). Debajo de la celda pulsa See performance. Verás la lista de sentencias Spark que ejecutó la celda. Elige una para ver sus métricas y pulsa See query profile. En jobs serverless: run del job → Timeline → flecha junto a la task → clic en la sentencia.

Requisito: ser el dueño de la query o tener al menos CAN MONITOR sobre el SQL warehouse que la ejecutó.

Si sale "Query profile is not available", la query salió de la caché de resultados y no hay perfil. La doc sugiere un cambio trivial, como cambiar o quitar el LIMIT, para forzar una ejecución real.

Limitaciones del perfil en serverless (notebooks y jobs)

Según la doc: no hay métricas verbose (el verbose mode no está), no se puede descargar el perfil, no hay acceso al Spark UI, el texto de la sentencia muestra solo la última línea ejecutada, y el perfil completo solo está disponible cuando la query termina (las métricas sí se actualizan en vivo).

Cómo funciona por dentroAnatomía de la pantalla

Un resumen con duración, I/O e insights, y un perfil detallado con el DAG de operadores.

El panel de detalles (el resumen)

  • Estado (Queued, Running, Finished, Failed, Cancelled), usuario, tipo de compute, ID de la ejecución y el texto de la query.
  • Métricas de la query bajo el texto. Algunas llevan un icono de filtro que indica el porcentaje de datos descartados (pruned) al escanear. Es el primer sitio donde ves el data skipping.
  • Query wall-clock duration: el tiempo total desde que empieza el scheduling hasta que termina la ejecución, con el desglose en scheduling, optimización de la query y file pruning, y ejecución.
  • Aggregated task time: el tiempo sumado de todas las tasks en todos los cores. Puede ser mucho mayor que el wall-clock si hubo mucho paralelismo, y menor si las tasks esperaron nodos libres.
  • Input/Output (IO): lo que se leyó y escribió.
  • See longest operators for this query: abre el panel Top operators.
  • Un resumen de los performance insights más importantes, ordenados por su efecto estimado en el tiempo total de las tasks.

El perfil detallado

  • A la izquierda, pestañas: Details (métricas resumen), Top operators (los operadores más caros), Query text y Performance insights (el detalle de cada insight).
  • A la derecha, el DAG. Un selector cambia la métrica que se reporta en cada nodo: Time spent, Memory peak o Rows. Puedes buscar operadores o columnas, hacer zoom y hacer clic en un operador para ver sus métricas en un panel lateral.
  • Enable verbose mode (menú de tres puntos) muestra métricas de operaciones que por defecto se ocultan porque casi nunca son el cuello de botella. No existe en serverless.
  • Open in Spark UI (mismo menú) solo para queries de Databricks SQL.
  • Colores de Photon. La doc de Photon dice que en el query profile los operadores Photon se ven en morado y los estándar en gris, y que la vista de detalles de ejecución muestra el porcentaje del tiempo de las tasks que corrió en Photon. En el Spark UI de un cluster clásico es otra paleta: Photon en naranja, Spark en azul.
  • Algunas operaciones no Photon se ejecutan en grupo y comparten métricas: todas muestran el mismo valor que el operador padre. No culpes a cada una por separado.

Los operadores más comunes, según la doc: Scan (lee de una fuente), Filter (aplica el WHERE), Join, Union, Shuffle (redistribuye datos entre executors, y es caro porque los mueve por la red) y Hash / Sort (agrupa por clave y aplica funciones como SUM o COUNT).

MétodoTres cuellos de botella del examen

El tipo de operador que domina el tiempo te dice qué familia de causas revisar. Abre el perfil, ordena por Time spent (o abre Top operators) y mira qué tipo de operador está arriba. Cada tipo apunta a una familia de causas.

Cuello de botellaDónde lo vesQué arreglas
Mal data skippingEl Scan domina el tiempo. Lee casi todos los archivos de la tabla y el porcentaje de pruning es bajo. Justo después, el Filter deja muy pocas filas (Rows cae varios órdenes de magnitud).Filtrar por las claves de clustering, o elegir claves que coincidan con los filtros reales (Liquid clustering). Insights posibles: COVERAGE_FILTER_KEYS_CLUSTERING, COVERAGE_STATS_DELTA, DATA_FILE_SIZE.
Join ineficiente(a) Join que explota: en Rows, la salida del join es mucho mayor que la suma de sus entradas. (b) Tipo equivocado: dos Shuffle grandes alimentan un join cuando uno de los lados es pequeño y podía ir por broadcast.(a) Corregir la condición, deduplicar o filtrar antes (insight EXPLODING_JOIN). (b) Hint BROADCAST para el lado pequeño (Joins, AQE).
Shuffle y spillLos Shuffle y el Aggregate o Join que viene después dominan el tiempo. En Memory peak ese operador es el más alto y en sus métricas aparece spill a disco. El agregado parcial casi no reduce filas.Reducir filas, columnas o columnas grandes antes del shuffle. En un SQL warehouse, subir el tamaño. Revisar skew (Remedios, Shuffle). Insights: DATA_SPILL, DATA_SKEW.
  • Sobre el broadcast. El hint BROADCAST evita el shuffle desde el inicio; AQE solo cambia a broadcast después de los dos shuffles. Umbrales y reglas en Estrategias de join. La doc de Photon dice que Photon reemplaza los sort-merge joins por hash joins, así que en serverless y en warehouses espera ver el join con shuffle como un hash join con dos Shuffle debajo (esto último lo deduzco de esa frase; la doc del query profile no lo dice).
  • Sobre el spill. El query profile no muestra tasks, así que la pista del skew suele llegar por el insight DATA_SKEW. Si el spill viene de skew, más particiones no lo arreglan (Remedios; mecanismo del spill en Memoria y OOM).
  • Lo que no es cuello de botella. Que el Scan sea el operador más caro es normal si lee solo lo necesario. Mira el pruning antes de concluir.

Las mismas señales a escalaDel perfil a system.query.history

Cada señal del perfil tiene una columna en system.query.history, y con ella buscas en todas las queries. El query profile es una query a la vez. Para buscar en todas, usa system.query.history (ver System tables). Cubre SQL warehouses, serverless para notebooks y jobs, y Lakeflow pipelines; no cubre clusters clásicos all-purpose o de jobs. Por defecto solo la ven los admins.

Señal del perfilColumnas de system.query.history
Pruning del Scanread_files, pruned_files, read_files_bytes, pruned_files_bytes. La doc define table_files = read_files + pruned_files y table_bytes = pruned_files_bytes + read_files_bytes.
Spillspilled_local_bytes (bytes escritos temporalmente a disco)
Shuffleshuffle_read_bytes (bytes enviados por la red)
Filas leídas y devueltasread_rows, produced_rows
Desglose del wall-clockcompilation_duration_ms (metadatos y optimización), execution_duration_ms, waiting_at_capacity_duration_ms (cola), waiting_for_compute_duration_ms, total_duration_ms
Aggregated task timetotal_task_duration_ms
 
-- Queries lentas de la última semana con sus señales de cuello de botella
SELECT statement_id,
       executed_by,
       total_duration_ms,
       read_files,
       pruned_files,
       ROUND(100 * pruned_files / NULLIF(read_files + pruned_files, 0), 1) AS pct_archivos_descartados,
       ROUND(read_files_bytes    / POWER(1024, 3), 1) AS leido_gib,
       ROUND(spilled_local_bytes / POWER(1024, 3), 1) AS spill_gib,
       ROUND(shuffle_read_bytes  / POWER(1024, 3), 1) AS shuffle_gib,
       read_rows,
       produced_rows
FROM system.query.history
WHERE start_time >= current_timestamp() - INTERVAL 7 DAYS
  AND execution_status = 'FINISHED'
  AND total_duration_ms > 60000
ORDER BY total_duration_ms DESC
LIMIT 50;

Las columnas están en la doc de la tabla. La query y el umbral de 60 s son míos. produced_rows son las filas que devuelve la sentencia: un join que explota y luego se agrega no se nota ahí, solo en el perfil.

Para saltar de una fila al perfil: copia el statement_id, entra al mismo workspace (workspace_id), abre Query History, pega el ID en el filtro Statement ID, haz clic en la query y luego en See query profile.

Cuidado con read_bytes

No se compara con table_bytes. Mide lo leído después del pruning de columnas y row groups, mezcla datos comprimidos de storage con datos sin comprimir de la caché de disco, y crece con los reintentos. Por eso puede superar el tamaño de la tabla.

Cómo se usaUn experimento en Free Edition

Provoca un join que explota y míralo en el perfil. Free Edition es serverless, así que tienes el query profile y no el Spark UI. Este experimento provoca un join que explota y lo compara con el join correcto.

-- 1 millón de pedidos y 1 millón de envíos; cliente_id se repite 1,000 veces en cada tabla
CREATE OR REPLACE TEMP VIEW pedidos AS
SELECT id AS pedido_id, id % 1000 AS cliente_id FROM range(1000000);

CREATE OR REPLACE TEMP VIEW envios AS
SELECT id AS envio_id, id AS pedido_id, id % 1000 AS cliente_id FROM range(1000000);

-- Celda A: join por la clave equivocada (1,000 × 1,000 × 1,000 = 1,000 millones de filas)
SELECT count(*) FROM pedidos p JOIN envios e ON p.cliente_id = e.cliente_id;

-- Celda B: join por la clave correcta (1 millón de filas)
SELECT count(*) FROM pedidos p JOIN envios e ON p.pedido_id = e.pedido_id;
  1. Ejecuta la celda A. Debajo, pulsa See performance y elige la sentencia. Mira el wall-clock y el aggregated task time del resumen.
  2. Pulsa See query profile. Cambia el grafo a Rows. Busca el join: entran 1 millón de filas por cada lado y salen alrededor de 1,000 millones.
  3. Cambia a Time spent y abre Top operators. El join y el agregado que cuenta su salida deberían estar arriba.
  4. Abre la pestaña Performance insights. Si Databricks detecta el patrón, aparece EXPLODING_JOIN.
  5. Ejecuta la celda B y compara los dos perfiles. Cambiaste una sola palabra de la condición.
  6. Para el data skipping, repite el experimento de Liquid clustering y compara en el Scan los archivos leídos y descartados antes y después del OPTIMIZE.
No ejecuté este experimento. Las cifras de filas salen de la aritmética de los datos. El tiempo, el aspecto exacto del grafo (si el join aparece como broadcast o con shuffle, por ejemplo) y si el insight EXPLODING_JOIN aparece en este caso dependen del motor. Verifícalo en tu workspace.

Cuándo usarlo y cuándo noQué herramienta para qué pregunta

El query profile es para una ejecución concreta en serverless o en un warehouse.

PreguntaHerramienta
¿Por qué esta query (en serverless o un warehouse) es lenta?Query profile
¿Qué sentencia de esta celda o de esta task de job tardó más?See performance en el notebook, o Timeline del job serverless
¿Qué queries de la semana tienen spill o poco pruning?system.query.history
¿Qué task de un stage tiene skew en un cluster clásico?Spark UI (ver Diagnóstico). El query profile no muestra tasks.
¿Qué plan va a elegir el optimizador antes de ejecutar?EXPLAIN. El query profile solo existe para ejecuciones reales.

Con qué se confundeCinco trampas

Cinco lecturas del perfil que llevan a conclusiones equivocadas.

  • Wall-clock vs aggregated task time. El primero es lo que esperó el usuario. El segundo es la suma de todas las tasks en todos los cores. Una query de 90 s con 3 horas de task time hizo mucho trabajo en paralelo: optimizarla ahorra cómputo aunque el usuario no lo note tanto.
  • Query insights vs performance insights. En serverless la doc llama query insights a lo que ves al pulsar See performance (la lista de sentencias y sus métricas). Los performance insights son las recomendaciones con nombre, como DATA_SPILL o EXPLODING_JOIN, que aparecen en el resumen y en su propia pestaña del perfil.
  • Morado y gris vs naranja y azul. Morado (Photon) y gris (estándar) en el query profile. Naranja (Photon) y azul (Spark) en el Spark UI. Un nodo gris en un warehouse suele indicar algo que Photon no soporta, como una UDF.
  • Sin perfil no significa error. "Query profile is not available" suele ser un acierto de la caché de resultados. Cambia el LIMIT y vuelve a ejecutar.
  • Accelerated no es un problema. Algunos insights llevan la etiqueta Accelerated: describen optimizaciones que Databricks ya aplicó, como HISTORY_BASED_JOIN_STRATEGY (eligió broadcast con base en ejecuciones anteriores) o AUTO_LIQUID_CLUSTERING. No piden acción.

Qué pasaría si

Abre cada pregunta para ver la respuesta.

…subes el tamaño del warehouse para la query del Scan sin data skipping?

Leerías los mismos 501 GiB con más cores. El wall-clock baja algo, pero el aggregated task time (y el coste) sigue igual o sube. El arreglo es leer menos: filtrar por las claves de clustering o cambiar las claves.

…pones BROADCAST en el lado grande de un join?

Ese lado se copia entero a cada executor. El hint se salta autoBroadcastJoinThreshold, pero no todos los límites: Apache Spark rechaza un broadcast de más de 8 GB (comportamiento de Spark, no aparece en la doc de Databricks), y antes de eso la memoria del driver y de los executors tiene que aguantar la tabla. Lo más probable es un error de memoria. El broadcast es para el lado pequeño.

…el perfil tiene spill pero el agregado parcial sí reduce mucho las filas?

Entonces el volumen total no explica el spill y conviene sospechar de skew: unas pocas claves concentran los datos. Busca el insight DATA_SKEW y revisa la distribución de la clave (Remedios).

…buscas en system.query.history una query de un cluster clásico?

No la vas a encontrar. La tabla cubre warehouses, serverless y Lakeflow pipelines. Para un cluster clásico usa el Spark UI.

…abres el perfil mientras la query sigue corriendo en serverless?

Ves métricas que se actualizan en vivo, pero el perfil completo solo aparece cuando la query termina. Espera a que acabe antes de sacar conclusiones.
