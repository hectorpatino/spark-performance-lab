Monitoreo con system tables: coste y rendimiento en SQL

Lo esencial en 1 minuto

  • Las system tables son tablas de solo lectura en el catálogo system de Unity Catalog. Son gratis (pagas el compute que las consulta) y por defecto solo las lee quien es account admin y metastore admin.
  • No son tiempo real: billing.usage llega normalmente en 12 h, y query.history y las tablas de jobs en 1 h. Filtra siempre por fecha.
  • Para el coste, une billing.usage con list_prices por el rango de vigencia del precio y suma todas las filas, también las RETRACTION y RESTATEMENT.
  • query.history cubre SQL warehouses, serverless y pipelines de Lakeflow, no clusters clásicos. Sus columnas clave son spilled_local_bytes, pruned_files y waiting_at_capacity_duration_ms.
  • Las tablas de jobs y clusters son SCD: toma la última fila por change_time. job_run_timeline parte las runs en filas por hora y solo la última trae result_state.

Si solo recuerdas una cosa: para enterarte sin mirar, pon una SQL alert sobre una de estas queries; para fallos y retrasos de un job, usa sus notificaciones.

Qué problema resuelveLa factura sube y nadie sabe por qué

Las system tables responden con SQL qué gastó, qué tardó y qué falló en toda la cuenta.

Llega el cierre de mes y el consumo de Databricks subió un 40 %. El Spark UI solo muestra la aplicación que tienes abierta. La Query History muestra queries una por una. Ninguna de las dos te dice qué job gastó más esta semana, qué warehouse tuvo cola el lunes o qué cluster interactivo quedó encendido todo el fin de semana con la CPU al 5 %.

Para eso necesitas los datos operativos de toda la cuenta en tablas que puedas consultar con SQL, unir entre sí y vigilar con alertas.

System tables son tablas de solo lectura que Databricks aloja en el catálogo system de Unity Catalog con los datos operativos de tu cuenta: facturación, precios, queries, compute, jobs, predictive optimization, auditoría y más. Sirven para observabilidad histórica. Son gratis; solo pagas el compute con el que las consultas.

Idea mentalEl libro contable y la caja negra

Casi todo el monitoreo consiste en unir la facturación con lo que pasó, por un ID común.

Piensa en dos libros. system.billing.usage es el libro contable: cada fila dice cuántas unidades se consumieron, en qué SKU y a nombre de qué recurso (job, warehouse, cluster, tag). Las demás tablas son la caja negra de vuelo: qué pasó dentro de cada query, de cada nodo y de cada run. El trabajo de monitoreo casi siempre es unir los dos libros por un ID común: usage_metadata.job_id con job_id, usage_metadata.cluster_id con cluster_id, usage_metadata.warehouse_id con compute.warehouse_id.

Por dentro · 1Dónde viven y quién las puede leer

Necesitas Unity Catalog y permisos explícitos; query history es la más restringida.

  • Unity Catalog es requisito. El catálogo system viene incluido en cada metastore. Hace falta al menos un workspace con Unity Catalog para habilitarlas, y solo se consultan desde un workspace con Unity Catalog. Aun así incluyen datos de los workspaces de la cuenta que no lo tienen.
  • Modelo de privilegios. El metastore tiene que estar en Unity Catalog Privilege Model Version 1.0.
  • Acceso por defecto. Solo quien es a la vez account admin y metastore admin. Para los demás, un admin concede USE CATALOG sobre system, y USE SCHEMA y SELECT sobre cada schema.
  • Regional o global. La mayoría son regionales: ves los workspaces de la región desde la que consultas. system.billing.usage y system.billing.list_prices son globales. Por eso un join de usage con clusters solo encuentra los clusters de tu región.
  • Query history es más restringida. Por defecto solo la ven los admins, y la doc recomienda dar acceso con una dynamic view por usuario o grupo. La columna statement_text devuelve <REDACTED> salvo para account admins o miembros del grupo databricks_pii_access.

Verifica en tu cuenta si algún schema (por ejemplo system.query) aparece vacío o deshabilitado antes de concluir que no tienes permisos.

Por dentro · 2Retención y frescura: no es tiempo real

Cada tabla tiene su retención y su retraso, y el retraso decide cuándo programar una alerta. La doc es explícita: no hay monitoreo en tiempo real y los datos se actualizan a lo largo del día. Cada tabla tiene su propio retraso típico. Ese retraso decide a qué hora puedes programar una alerta sin que le falten datos.

Cuatro matices: retención configurable, consultas poco selectivas, schema que crece y streaming
  • Retención configurable (Beta). Si el account admin activa el preview System Tables Configurable Retention, la retención gratuita pasa a 395 días para las tablas soportadas y se puede fijar entre 30 y 3.650 días (setting st_retention). Lo que pase de 395 días se cobrará como almacenamiento cuando sea GA.
  • Consultas poco selectivas fallan. Si no filtras lo suficiente, recibes System Table query returned too much data. Please repeat query with more selective predicates. Filtra siempre por fecha.
  • El schema crece. Pueden aparecer columnas nuevas en cualquier momento. Si copias estas tablas a otra, activa schema evolution y no uses SELECT * en vistas que dependan de un orden fijo.
  • Streaming. Las tablas que lo admiten se leen en streaming desde DBR 16.4 con skipChangeCommits = true. No todas lo admiten: según la columna Supports streaming de la referencia, system.query.history, system.billing.list_prices, system.storage.predictive_optimization_operations_history, system.compute.node_types y system.alert.* no admiten streaming. Tienen VACUUM de 7 días, así que un stream que se atrase más de 7 días puede romperse.

MapaQué tabla responde qué pregunta

Busca tu pregunta en la segunda columna y lee la tercera antes de escribir la query.

Cómo se usaQueries listas para correr

Diez queries de coste, rendimiento y jobs, cada una con su lectura y su fuente. Todas se pueden pegar en el SQL editor de un SQL warehouse. Cambia los valores entre < >. Cada una indica la tabla y la página de la doc donde se verifican sus columnas.

1. ¿Qué jobs cuestan más en los últimos 30 días?

WITH jobs AS (            -- jobs es SCD2: última versión de cada job
  SELECT workspace_id, job_id, name
  FROM system.lakeflow.jobs
  QUALIFY ROW_NUMBER() OVER (PARTITION BY workspace_id, job_id ORDER BY change_time DESC) = 1
),
uso AS (
  SELECT u.workspace_id,
         u.usage_metadata.job_id   AS job_id,
         u.usage_metadata.job_name AS job_name_serverless,
         u.usage_quantity,
         u.usage_quantity * p.pricing.effective_list.default AS usd
  FROM system.billing.usage u
  LEFT JOIN system.billing.list_prices p
    ON  u.sku_name = p.sku_name
    AND u.usage_end_time >= p.price_start_time
    AND (p.price_end_time IS NULL OR u.usage_end_time < p.price_end_time)
    AND p.currency_code = 'USD'
  WHERE u.billing_origin_product = 'JOBS'
    AND u.usage_metadata.job_id IS NOT NULL
    AND u.usage_date >= CURRENT_DATE() - INTERVAL 30 DAY
)
SELECT uso.workspace_id, uso.job_id,
       coalesce(MAX(uso.job_name_serverless), MAX(jobs.name)) AS job_name,
       ROUND(SUM(uso.usage_quantity), 1) AS dbus,
       ROUND(SUM(uso.usd), 2)            AS usd_lista
FROM uso
LEFT JOIN jobs USING (workspace_id, job_id)
GROUP BY uso.workspace_id, uso.job_id
ORDER BY usd_lista DESC
LIMIT 20;

Cómo leerlo. Dos o tres jobs suelen concentrar casi todo el gasto: empieza por ellos. El join con list_prices usa el rango de vigencia del precio, como en la doc; unir solo con price_end_time IS NULL aplica el precio de hoy a consumos viejos. El nombre sale de usage_metadata.job_name (solo serverless) o de la última fila de system.lakeflow.jobs. Los jobs que corren en clusters all-purpose no aparecen, porque ahí no se llena job_id.

Tablas: billing.usage Azure, billing.list_prices Azure, lakeflow.jobs Azure. La doc tiene una versión por run en "Calculate cost per job run".

2. ¿Cómo evoluciona el coste diario por producto?

SELECT u.usage_date,
       u.billing_origin_product,
       ROUND(SUM(u.usage_quantity * p.pricing.effective_list.default), 2) AS usd_lista
FROM system.billing.usage u
JOIN system.billing.list_prices p
  ON  p.sku_name = u.sku_name
  AND u.usage_end_time >= p.price_start_time
  AND (p.price_end_time IS NULL OR u.usage_end_time < p.price_end_time)
  AND p.currency_code = 'USD'
WHERE u.usage_date >= CURRENT_DATE() - INTERVAL 30 DAY
GROUP BY ALL
ORDER BY u.usage_date, usd_lista DESC;

Cómo leerlo. billing_origin_product separa JOBS, SQL, ALL_PURPOSE, DLT, PREDICTIVE_OPTIMIZATION y otros. Esto importa porque predictive optimization, data quality monitoring y los jobs serverless comparten el mismo SKU: con sku_name no los distingues. Un pico aislado en ALL_PURPOSE suele ser un cluster interactivo que no se apagó; revisa su auto_termination_minutes en system.compute.clusters. El último día suele verse bajo porque los registros tardan hasta 12 horas en llegar.

Tablas: Monitor costs using system tables Azure (de ahí sale el patrón del join con precios).

3. ¿Qué queries hacen spill a disco?

SELECT statement_id, executed_by, compute.warehouse_id,
       ROUND(spilled_local_bytes / POW(1024, 3), 2) AS spill_gb,
       ROUND(read_bytes / POW(1024, 3), 2)          AS read_gb,
       ROUND(total_duration_ms / 1000, 1)           AS duracion_s,
       start_time, statement_text
FROM system.query.history
WHERE start_time >= NOW() - INTERVAL 7 DAY
  AND spilled_local_bytes > 0
  -- AND compute.warehouse_id = '<warehouse-id>'
ORDER BY spilled_local_bytes DESC
LIMIT 50;

Cómo leerlo. spilled_local_bytes es lo que la query escribió temporalmente a disco por falta de memoria. En un SQL warehouse, la doc recomienda subir el tamaño del warehouse o optimizar la query. Para ver dónde ocurre, copia el statement_id, ve a Query History, pégalo en el filtro Statement ID y abre See query profile. El mismo diagnóstico en el Spark UI está en Diagnóstico.

Tabla: query.history Azure. Basada en Example queries for monitoring SQL warehouse activity Azure.

4. ¿Qué queries grandes casi no podan archivos?

SELECT statement_id, executed_by,
       read_files, pruned_files,
       ROUND(100 * pruned_files / NULLIF(read_files + pruned_files, 0), 1) AS pct_podado,
       ROUND(read_files_bytes / POW(1024, 3), 2) AS leidos_gb,
       ROUND(total_duration_ms / 1000, 1)        AS duracion_s,
       statement_text
FROM system.query.history
WHERE start_time >= NOW() - INTERVAL 7 DAY
  AND execution_status = 'FINISHED'
  AND statement_type = 'SELECT'
  AND read_files_bytes > 10 * POW(1024, 3)      -- solo lecturas de más de 10 GB
ORDER BY pct_podado ASC, read_files_bytes DESC
LIMIT 50;

Cómo leerlo. La doc define el total de archivos de las tablas leídas como read_files + pruned_files, y su tamaño comprimido como read_files_bytes + pruned_files_bytes. Un pct_podado cercano a 0 con muchos GB leídos indica que el filtro no coincide con cómo están organizados los archivos: revisa las claves de liquid clustering. Una query sin WHERE también da 0 %, y eso es correcto. No compares read_bytes con estos tamaños: read_bytes mezcla datos comprimidos con datos de la disk cache sin comprimir y puede ser mayor que la tabla.

Tabla: query.history Azure, sección "Understanding scan metrics". El umbral de 10 GB es nuestro.

5. ¿Cuánto esperan las queries en cola en un warehouse?

SELECT DATE(start_time) AS dia,
       COUNT(*) AS queries,
       ROUND(AVG(waiting_at_capacity_duration_ms) / 1000, 1)              AS cola_media_s,
       ROUND(PERCENTILE(waiting_at_capacity_duration_ms, 0.95) / 1000, 1) AS cola_p95_s,
       ROUND(AVG(waiting_for_compute_duration_ms) / 1000, 1)              AS arranque_medio_s,
       ROUND(PERCENTILE(total_duration_ms, 0.95) / 1000, 1)               AS duracion_p95_s
FROM system.query.history
WHERE compute.warehouse_id = '<warehouse-id>'
  AND start_time >= NOW() - INTERVAL 30 DAY
GROUP BY DATE(start_time)
ORDER BY dia;

Cómo leerlo. Son dos esperas distintas. waiting_at_capacity_duration_ms es tiempo en cola porque el warehouse ya estaba lleno: la doc recomienda subir max clusters para que escale. waiting_for_compute_duration_ms es tiempo esperando a que se aprovisione compute, por ejemplo cuando el warehouse estaba detenido. Si lo que sube es duracion_p95_s sin cola, el problema está en las queries o en el tamaño del warehouse.

Tabla: query.history Azure. Adaptada de "Analyze query performance trends over time" en la página de monitoreo de warehouses Azure.

6. ¿Qué clusters clásicos tienen la CPU ociosa o la memoria al límite?

WITH clusters AS (        -- clusters es SCD: última configuración
  SELECT workspace_id, cluster_id, cluster_name, cluster_source, worker_node_type
  FROM system.compute.clusters
  QUALIFY ROW_NUMBER() OVER (PARTITION BY workspace_id, cluster_id ORDER BY change_time DESC) = 1
)
SELECT n.cluster_id, c.cluster_name, c.cluster_source, c.worker_node_type, n.driver,
       COUNT(DISTINCT n.instance_id)                          AS nodos,
       ROUND(AVG(n.cpu_user_percent + n.cpu_system_percent), 1) AS cpu_media_pct,
       ROUND(MAX(n.mem_used_percent), 1)                      AS mem_max_pct,
       ROUND(MAX(n.mem_swap_percent), 2)                      AS swap_max_pct,
       ROUND(AVG(n.cpu_wait_percent), 1)                      AS io_wait_media_pct
FROM system.compute.node_timeline n
LEFT JOIN clusters c USING (workspace_id, cluster_id)
WHERE n.start_time >= NOW() - INTERVAL 7 DAY
GROUP BY ALL
HAVING AVG(n.cpu_user_percent + n.cpu_system_percent) < 20
    OR MAX(n.mem_used_percent) > 90
ORDER BY mem_max_pct DESC;

Cómo leerlo. Cada fila de node_timeline es un minuto de un nodo. CPU media baja en un cluster interactivo grande sugiere que sobra tamaño o que le falta auto-terminación. Memoria máxima por encima del 90 % con swap distinto de cero en los workers es una señal de presión de memoria: riesgo de spill o de OOM. Mira si es el driver (driver = true) o los workers, porque el remedio es distinto. Para comparar con el hardware, une worker_node_type con system.compute.node_types (core_count, memory_mb).

Tablas: compute.node_timeline, compute.clusters, compute.node_types Azure. Solo clusters clásicos (all-purpose, jobs, pipelines). Los umbrales de 20 % y 90 % son nuestros.

7. ¿Cuántas runs de jobs fallan cada día?

SELECT workspace_id,
       to_date(period_end_time) AS dia,
       result_state,
       COUNT(DISTINCT run_id)   AS runs
FROM system.lakeflow.job_run_timeline
WHERE period_end_time >= CURRENT_TIMESTAMP() - INTERVAL 30 DAYS
  AND result_state IS NOT NULL     -- solo la última fila de cada run trae result_state
GROUP BY ALL
ORDER BY dia;

Cómo leerlo. Los valores de result_state son SUCCEEDED, FAILED, SKIPPED, CANCELLED, TIMED_OUT, ERROR y BLOCKED. Escribir 'SUCCESS' o 'CANCELED' devuelve cero filas sin avisar. Para la causa, mira termination_code (por ejemplo CLUSTER_ERROR, LIBRARY_INSTALLATION_ERROR, MAX_CONCURRENT_RUNS_EXCEEDED). Una run que nunca empezó aparece con period_start_time = period_end_time.

Tabla: lakeflow.job_run_timeline Azure (Result state values, Termination code values).

8. ¿Qué task de un job es la más lenta?

SELECT task_key,
       COUNT(DISTINCT run_id)              AS ejecuciones,
       ROUND(AVG(duracion_s) / 60, 1)      AS media_min,
       ROUND(PERCENTILE(duracion_s, 0.95) / 60, 1) AS p95_min,
       ROUND(MAX(duracion_s) / 60, 1)      AS max_min
FROM (
  SELECT workspace_id, job_id, run_id, task_key,
         CAST(SUM(period_end_time - period_start_time) AS LONG) AS duracion_s
  FROM system.lakeflow.job_task_run_timeline
  WHERE job_id = '<job-id>'
    AND period_start_time >= CURRENT_TIMESTAMP() - INTERVAL 30 DAYS
  GROUP BY ALL
) t
GROUP BY task_key
ORDER BY p95_min DESC;

Cómo leerlo. La duración se suma desde las filas por hora, igual que hace la doc con las runs. No uses run_duration_seconds de job_run_timeline: vale 0 en jobs multi-task. Una p95 muy por encima de la media indica runs irregulares: días con más datos, skew o espera por recursos. Busca esas runs en la vista de matriz del job.

Tabla: lakeflow.job_task_run_timeline Azure.

9. ¿En qué tablas gasta predictive optimization?

SELECT catalog_name, schema_name, table_name, operation_type,
       COUNT(DISTINCT operation_id)  AS operaciones,
       ROUND(SUM(usage_quantity), 2) AS dbus_estimados
FROM system.storage.predictive_optimization_operations_history
WHERE usage_unit = 'ESTIMATED_DBU'
  AND timestampdiff(day, start_time, now()) < 30
GROUP BY ALL
ORDER BY dbus_estimados DESC
LIMIT 20;

Cómo leerlo. operation_type puede ser COMPACTION, VACUUM, ANALYZE, CLUSTERING, AUTO_CLUSTERING_COLUMN_SELECTION, DATA_SKIPPING_COLUMN_SELECTION, COMPATIBILITY_MODE_REFRESH, DELETE o PURGE. Mira también operation_status: un FAILED: PRIVATE_LINK_SETUP_ERROR indica que falta conectividad privada para serverless hacia tu storage. En system.billing.usage este gasto aparece con billing_origin_product = 'PREDICTIVE_OPTIMIZATION'. Si una tabla ya está bajo predictive optimization, un job propio de OPTIMIZE sobre ella es gasto duplicado.

Tabla: storage.predictive_optimization_operations_history Azure (Public Preview).

10. ¿Qué jobs corren en clusters all-purpose?

with clusters AS (
  SELECT *, ROW_NUMBER() OVER(PARTITION BY workspace_id, cluster_id ORDER BY change_time DESC) as rn
  FROM system.compute.clusters
  WHERE cluster_source="UI" OR cluster_source="API"
  QUALIFY rn=1
),
job_tasks_exploded AS (
  SELECT workspace_id, job_id, EXPLODE(compute_ids) as cluster_id
  FROM system.lakeflow.job_task_run_timeline
  WHERE period_start_time >= CURRENT_DATE() - INTERVAL 30 DAY
  GROUP BY ALL
),
all_purpose_cluster_jobs AS (
  SELECT t1.*, t2.cluster_name, t2.owned_by, t2.dbr_version
  FROM job_tasks_exploded t1
    INNER JOIN clusters t2 USING (workspace_id, cluster_id)
)
SELECT * FROM all_purpose_cluster_jobs LIMIT 10;

Cómo leerlo. Es la query de la doc, sin cambios. cluster_source vale UI o API solo para compute all-purpose; el compute de jobs aparece como JOB. Un job en all-purpose tiene dos problemas: comparte recursos con notebooks y su coste no se puede atribuir con exactitud, porque usage_metadata.job_id no se llena. La doc recomienda job compute o serverless.

Tablas: lakeflow.job_task_run_timeline + compute.clusters Azure, "Find jobs running on all-purpose compute".

AlertasDe una query a una SQL alert

Una SQL alert convierte cualquiera de estas queries en un aviso programado. Una Databricks SQL alert ejecuta una query con un horario, evalúa una condición sobre el resultado y notifica cuando se cumple. Cada evaluación termina en OK, TRIGGERED o ERROR. La versión actual ya no tiene el estado UNKNOWN de las alertas legacy, y cada alerta tiene su propia query: no reutiliza una query guardada.

  1. Crea la alerta. En la barra lateral, Alerts > Create Alert.
  2. Escribe la query. Que devuelva pocas filas y una columna clara para comparar. Las alertas no aceptan queries con parámetros, así que la fecha va en el SQL (current_date() - 1), no en un :parametro.
  3. Elige el compute. El SQL warehouse que ejecutará la query en cada evaluación.
  4. Define la condición. El valor a comprobar es el primer valor de una columna o una agregación sobre todas las filas de esa columna (por ejemplo SUM o AVERAGE); luego el operador (por ejemplo >) y el umbral, que por defecto es Static value. Pulsa Test condition para ver si dispararía con los datos de hoy.
  5. Notificaciones. Usuarios o notification destinations (Slack, Microsoft Teams, PagerDuty, webhooks, que crea un workspace admin). Opcionalmente, una frecuencia para repetir la notificación hasta que la alerta vuelva a OK.
  6. Horario. En el icono de calendario, Edit schedule. Puedes marcar Show cron syntax y escribirlo en Quartz cron.
  7. Advanced. Notify on OK (avisar cuando se normaliza), Empty result state (qué estado dar si la query no devuelve filas) y Template para personalizar el mensaje con variables como {{ALERT_NAME}}, {{ALERT_STATUS}} o {{QUERY_RESULT_TABLE}} (primeras 100 filas; HTML solo se ve en email).

Una alerta también puede ser una task dentro de un job (SQL alert task), para que las tasks siguientes del job dependan del resultado. Cada workspace admite por defecto 250 ejecuciones de alertas activas a la vez; si todas se programan a la misma hora, algunas se saltan. La doc recomienda escalonar los horarios.

Lakeflow JobsNotificaciones y umbrales de un job

Para fallos y retrasos de un job, usa sus notificaciones y su duration warning, no una query. Las SQL alerts vigilan el resultado de una query. Las notificaciones de un job reaccionan a eventos de sus runs. Un job o una task pueden notificar en estos eventos:

  • Start, Success y Failure.
  • Duration warning: la run supera la duración esperada que configuraste.
  • Streaming backlog: una métrica de backlog supera su umbral.
  • Maintenance start y Maintenance complete, en jobs continuos con ventana de mantenimiento. Estos dos no admiten email; usa un system destination.

En la UI de Lakeflow Jobs

  1. En el panel Job details, abre Duration and streaming backlog thresholds. Con la métrica Run duration, el campo Warning es la duración esperada (solo genera un evento) y el campo Timeout es la máxima: si la run no termina a tiempo queda como Timed Out. Para un umbral de streaming, elige la métrica de backlog y su valor.
  2. En Job notifications, Edit notifications > Add notification. Elige Email address o un system destination y marca los eventos: Start, Success, Failure, Duration warning o Streaming backlog.
  3. Para reducir ruido, marca Mute notifications for skipped runs o Mute notifications for canceled runs. En notificaciones de task existe además Mute notifications until the last retry.
Permisos, límites y casos en que no llega el aviso
  • Necesitas permiso CAN MANAGE o IS OWNER sobre el job.
  • Máximo tres system destinations por tipo de evento en cada job o task.
  • Las notificaciones a nivel de job no se envían cuando se reintenta una task fallida. Si quieres un aviso por cada fallo de task, configura la notificación en la task.
  • Un job que termina en Succeeded with failures cuenta como éxito: para enterarte tienes que marcar Success.
  • El backlog se evalúa como media de 10 minutos; mientras siga alto, el aviso se repite cada 30 minutos. No funciona en pipeline tasks (para pipelines, usa una SQL alert sobre el event log o event hooks) y deja de funcionar si el código usa awaitTermination().
  • Las métricas de backlog dependen de la fuente: Kafka da bytes y records; Kinesis, bytes y seconds; Delta y Auto Loader, bytes y files. Es Public Preview.

Lo mismo como configuración del job

Los campos son los de la API de Jobs, y los mismos que acepta un bundle. Las métricas de health.rules documentadas son RUN_DURATION_SECONDS, STREAMING_BACKLOG_BYTES, STREAMING_BACKLOG_RECORDS, STREAMING_BACKLOG_SECONDS y STREAMING_BACKLOG_FILES.

CLI y REST APIConsultar runs sin abrir la UI

Para lo que pasa ahora mismo con un job, el CLI o la API son más rápidos que las system tables. Las system tables llegan con hasta una hora de retraso. Para saber qué pasa ahora con un job concreto, usa el CLI o la API de Jobs. Estos comandos están en la referencia del CLI:

# Buscar un job por nombre exacto (sin distinguir mayúsculas)
databricks jobs list --name "merge_clientes_silver" -o json

# Últimas 25 runs terminadas de un job, de la más reciente a la más antigua
databricks jobs list-runs --job-id 123456789 --completed-only --limit 25 -o json

# Runs en curso ahora mismo
databricks jobs list-runs --job-id 123456789 --active-only -o json

# Detalle de una run (estado, tasks, tiempos)
databricks jobs get-run 987654321 -o json

# Salida de una task: requiere el run_id de la TASK, no el de la run del job
databricks jobs get-run-output 555666777

# Volver a correr solo las tasks fallidas de una run, sin esperar a que termine
databricks jobs repair-run 987654321 --rerun-all-failed-tasks --no-wait
Más opciones y límites del CLI
  • list-runs admite también --run-type (JOB_RUN, SUBMIT_RUN, WORKFLOW_RUN) y --start-time-from / --start-time-to.
  • get-run-output devuelve como máximo los primeros 5 MB, y las runs se eliminan automáticamente a los 60 días.
  • Sin --no-wait, repair-run y run-now se quedan esperando a que la run llegue a TERMINATED o SKIPPED, hasta 20 minutos por defecto (--timeout).
  • run-now y repair-run aceptan --performance-target con PERFORMANCE_OPTIMIZED o STANDARD para jobs serverless.
  • Usa -p <perfil> para elegir el workspace de tu ~/.databrickscfg.
# Lo mismo por REST, con un token en DATABRICKS_TOKEN
curl -s -H "Authorization: Bearer $DATABRICKS_TOKEN" \
  "https://adb-<workspace-id>.<n>.azuredatabricks.net/api/2.2/jobs/runs/list?job_id=123456789&completed_only=true&limit=25"
La doc de Azure confirma que existe la API 2.2 de Jobs, pero no pude abrir la referencia de la API para comprobar la ruta exacta /api/2.2/jobs/runs/list ni las unidades de --start-time-from (la API suele usar milisegundos epoch). Verifícalo en la referencia de la API de Jobs, endpoint "List job runs".

Fuente: jobs command group Azure.

Coste en AzureLo que las system tables no te cobran

En compute clásico, la factura real es mayor que lo que ves en billing.usage.

  • DBUs más infraestructura. Según la guía de optimización de costes, el coste total del compute clásico es DBUs más máquinas virtuales, discos y red, que Azure factura aparte. En serverless, el DBU ya incluye las máquinas virtuales. Por eso un cluster clásico cuesta más de lo que ves en system.billing.usage.
  • Precio de lista. system.billing.list_prices guarda precios publicados. Si tu empresa tiene descuentos o compró capacidad por adelantado (Databricks commit units, DBCU), la factura real es menor que usd_lista. El descuento de DBCU solo aplica a los DBUs; compute, storage y red se cobran aparte.
  • Tags en los dos lados. Los custom tags de workspaces, clusters, pools y SQL warehouses se propagan a custom_tags en system.billing.usage y a los recursos de Azure. Con los mismos tags puedes cuadrar el coste de DBUs con el de VMs en Cost analysis de Microsoft Cost Management.
  • Detalles de Azure en las tablas. cloud = 'AZURE'; usage_metadata.metastore_id nunca se llena en Azure Databricks; los tipos de nodo usan nombres de Azure como Standard_D16s_v3; azure_attributes.availability en system.compute.clusters muestra valores como ON_DEMAND_AZURE.
  • Dashboards listos. Los account admins pueden importar un dashboard de monitoreo de costes prediseñado y personalizable (Usage dashboards), construido sobre estas mismas tablas.

Con qué se confunde

Valores y columnas que se parecen y no significan lo mismo.

  • result_state y termination_code. En las tablas de jobs, result_state usa SUCCEEDED; termination_code usa SUCCESS. Y la ortografía cambia entre tablas: los jobs usan CANCELLED, mientras que query history y pipeline_update_timeline usan CANCELED.
  • waiting_at_capacity y waiting_for_compute. La primera es cola por warehouse lleno (más max clusters); la segunda es esperar a que arranque o se aprovisione compute.
  • pricing.default y pricing.effective_list.default. El primero sirve para estimaciones simples a largo plazo; el segundo resuelve las promociones y es el que la doc describe para calcular el coste. Algunas queries de la doc usan uno y otras el otro.
  • Duration warning y timeout. El warning solo dispara una notificación y la run sigue. El timeout la detiene y la marca como Timed Out.
  • SQL alert y notificación de job. La alerta evalúa una query con un horario; la notificación reacciona a un evento de una run. Para una alerta sobre el event log de un pipeline (por ejemplo backlog), necesitas una SQL alert, porque las notificaciones de backlog no aplican a pipeline tasks.
  • system.compute y los SQL warehouses. clusters y node_timeline no tienen warehouses ni serverless. Para warehouses usa warehouse_events, warehouses y query.history.

Qué pasaría si

Errores habituales al consultar estas tablas y lo que provocan.

  • Consultas system.query.history sin filtro de fecha: puede fallar con System Table query returned too much data.
  • Cuentas runs sin result_state IS NOT NULL: una run de tres horas cuenta tres o cuatro veces, una por cada fila horaria (con los cortes alineados al reloj desde enero de 2026, una run de 3 h puede ocupar 4 filas; fuente Azure). Y un run reparado tiene una fila con result_state por intento: cuenta con COUNT(DISTINCT run_id).
  • Filtras delete_time IS NULL antes de tomar la última fila de jobs: los jobs borrados aparecen con su último estado previo al borrado. La doc pide el orden inverso.
  • Sumas run_duration_seconds: obtienes ceros en casi todos los jobs actuales, porque solo se llena en jobs de una task creados con la API legacy.
  • Tu equipo no ve query history aunque tiene SELECT en otros schemas: por defecto es solo para admins. Crea una dynamic view.
  • Pones una alerta horaria con notificación en cada evaluación: un solo día malo genera 24 mensajes y 720 ejecuciones de la query al mes en tu warehouse.
  • Tu job de streaming llama awaitTermination(): el servicio de Jobs no puede seguir el stream y las notificaciones de backlog no llegan.
