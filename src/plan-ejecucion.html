Plan de ejecución: jobs, stages y tasks

Fuentes: Apache Spark · Cluster overview (glosario), Apache Spark · Web UI, Apache Spark · RDD operations (transformaciones y acciones), Databricks · EXPLAIN Azure y Databricks · Adaptive query execution Azure.

Lo esencial en 1 minuto

  • Las transformaciones (filter, select, groupBy, join) son lazy: solo anotan el plan. Cada acción (write, count, collect, show) lanza un job.
  • El plan lógico de un job es todo el linaje hasta su acción. Catalyst lo optimiza y elige un plan físico, que ves con explain().
  • Cada Exchange (shuffle) del plan físico corta un stage. Lo narrow que va seguido cabe en el mismo stage.
  • Cada partición es una task. Los cores no cambian cuántas tasks hay, solo cuántas corren a la vez.
  • Sin cache(), cada acción recalcula su linaje desde la lectura.

Si solo recuerdas una cosa: para saber cuántos stages tendrá un job, cuenta los Exchange de su plan físico y súmale uno.

Qué problema resuelveSaber de dónde sale cada fila del Spark UI

Abres la pestaña Jobs y ves Job 0, Job 1, Job 2… con stages y tasks que no escribiste. Cada uno lo creó algo concreto de tu código: una acción, un shuffle o una partición. Si sabes qué crea cada nivel, puedes ir de la fila lenta del Spark UI a la línea del notebook que la causó.

Cómo funciona por dentroDe la acción a las tasks

    
    
      
  1. La acción crea el job. Mientras solo encadenas transformaciones no pasa nada. Al llamar a write, count o collect, el driver crea un job.
    2. 
      
  2. El job tiene su plan lógico. Es todo el linaje del DataFrame hasta esa acción, desde la lectura. Catalyst lo optimiza y elige un plan físico, que es el que ves con explain() y en la pestaña SQL / DataFrame del Spark UI.
    3. 
      
  3. El plan se corta en cada Exchange. Todo lo que va seguido sin shuffle (scan, filter, select, agregación parcial) cabe en un mismo stage, y Spark lo fusiona en un bloque WholeStageCodegen. Cada Exchange obliga a terminar un stage y empezar otro.
    4. 
      
  4. Cada stage tiene una task por partición. El primer stage tiene tantas tasks como trozos de entrada (~128 MB cada uno). Los stages que leen un shuffle tienen tantas como spark.sql.shuffle.partitions, o menos si AQE une particiones.
    5. 
      
  5. Un stage espera al anterior. El stage que lee un shuffle necesita los bloques de todas las map tasks, así que no empieza hasta que el stage anterior termina. Dos stages independientes, como los dos lados de un join, sí pueden correr a la vez.
    6. 
    

    
Qué pasa después, cuando esas tasks se reparten entre los cores, está en Tasks, cores y waves.


    
Cómo se usaEjemplo que puedes correr


df  = spark.range(0, 50_000_000, numPartitions=40)
agg = df.groupBy((df.id % 1000).alias("k")).count()

agg.explain()   # cada Exchange del plan es una frontera de stage
agg.collect()   # la acción: aquí se lanza el job

    
En el plan verás HashAggregate (parcial), Exchange hashpartitioning(k, …) y otro HashAggregate (final). Son dos stages: el primero con 40 tasks y el segundo con las particiones del shuffle (o menos, si AQE las une).

    
Usa collect() y no count() como acción: count() agregaría su propio stage de 1 task para sumar los conteos, como viste en el Simulador 1. Para ver los dos planes, el lógico optimizado y el físico, usa agg.explain(True) o agg.explain("formatted"). Con AQE, el plan definitivo solo se conoce al ejecutar: míralo en la pestaña SQL / DataFrame del Spark UI o en el query profile (ver AQE).


    
Con qué se confunde

    
    
      
  • Stage vs operación. Un stage no es una operación. Agrupa todas las operaciones narrow seguidas hasta el siguiente shuffle.
    • 
      
  • Job vs acción. En principio, una acción da un job. Con AQE y broadcast es normal ver varios jobs por una sola acción, porque cada query stage se lanza aparte.
    • 
      
  • Task vs partición. Es una relación 1:1 dentro de un stage. Cambiar las particiones es cambiar las tasks.
    • 
      
  • Transformación vs acción. Una transformación devuelve otro DataFrame y no ejecuta nada. Una acción devuelve un resultado al driver o escribe datos, y es lo único que lanza jobs.
    • 
      
  • Skipped stages. En el Spark UI aparecen como skipped cuando el shuffle que producían ya estaba escrito y se reutiliza. No es un error.
    • 
    


    
Qué pasaría si

    
    
      
  • Llamas a count() para "ver cuántas filas hay" antes de un write: lanzas un job extra que lee y procesa todo otra vez. Si ese linaje es caro, cuesta casi lo mismo que el write.
    • 
      
  • Haces df.cache() antes de dos acciones: la primera acción calcula y guarda df; la segunda lee de la caché y se salta la lectura y las transformaciones anteriores.
    • 
      
  • Encadenas cinco filter y select: el número de stages no cambia. Son narrow y van fusionados en el mismo bloque WholeStageCodegen.
