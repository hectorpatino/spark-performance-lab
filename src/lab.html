Lab: provocar skew y verlo

Base: notebook oficial AQE Demo (crea una tabla sales donde el item 100 está en el 80% de las ventas).

Lo esencial en 1 minuto

  • Free Edition es serverless: no hay Spark UI y solo puedes cambiar seis propiedades de Spark, entre ellas spark.sql.shuffle.partitions. AQE se queda encendido.
  • Detecta el skew sin UI contando filas por clave con groupBy(clave).count().
  • Una ventana PARTITION BY sobre la clave caliente manda todas sus filas a una sola task, y AQE no parte ventanas.
  • Una agregación combinable como max sufre mucho menos, porque se reduce dentro de cada partición antes del shuffle.
  • Cambiar el número de particiones no arregla el skew; el salting en dos fases o rediseñar el cálculo sí.

Si solo recuerdas una cosa: la clave caliente decide el tiempo del stage, y AQE solo la parte en joins.

Antes de empezar. El notebook original desactiva y ajusta configs de AQE para comparar antes y después. En serverless (y Free Edition es serverless) solo se pueden cambiar unas pocas propiedades: spark.sql.shuffle.partitions, spark.sql.files.maxPartitionBytes, spark.sql.ansi.enabled, spark.sql.session.timeZone, spark.sql.legacy.timeParserPolicy y spark.databricks.execution.timeout (fuente Azure). Por eso adapté el lab: no apagamos AQE, sino que buscamos un caso donde AQE no te salva y lo arreglamos a mano.
No pude leer el contenido celda por celda del notebook original (la página no devolvió el código). Lo que sigue es mi adaptación con la misma idea de datos. Para ver el perfil en serverless: en la celda pulsa See performance, elige la instrucción y luego See query profile (doc de Azure Databricks).
  1. Crea datos con skew deliberado (20 M filas, 80% con product_id = 100). 
    from pyspark.sql import functions as F
from pyspark.sql.window import Window

sales = (spark.range(20_000_000)
  .withColumn("product_id",
      F.when(F.rand(seed=1) < 0.8, F.lit(100))
       .otherwise((F.rand(seed=2) * 100_000).cast("int")))
  .withColumn("amount", F.round(F.rand(seed=3) * 100, 2)))
  2. Detéctalo sin UI. Es el método más simple de la guía de optimización: contar filas por la clave del join o la agregación. 
    (sales.groupBy("product_id").count()
      .orderBy(F.desc("count")).show(5))
# Esperado: product_id 100 con ~16 M filas; el resto con ~40 cada uno
  3. Caso lento: ventana sobre la clave caliente. Un acumulado por producto obliga a ordenar todas las filas de cada producto juntas. Las ~16 M filas del producto 100 van a una sola task, y AQE no parte ventanas. 
    w = Window.partitionBy("product_id").orderBy("amount")
running = sales.withColumn("acumulado", F.sum("amount").over(w))
running.agg(F.max("acumulado")).collect()
    Abre el query profile de esa celda (See performance → See query profile). Busca el operador de ventana / sort: verás que se lleva casi todo el tiempo. El query profile muestra operadores, no tasks; para ver la task lenta en sí necesitas el Spark UI de un compute clásico (ver Query profile y Leer el Spark UI).
  4. Contraste: una agregación combinable no sufre igual. max se calcula primero dentro de cada partición y luego se combina (agregación parcial). Antes del shuffle, la clave caliente ya está reducida a una fila por partición. 
    top_agg = sales.groupBy("product_id").agg(F.max("amount").alias("max_amount"))
top_agg.count()
    Compara tiempos. Lección: si tu cálculo admite reescribirse como agregación combinable, hazlo. Un acumulado no lo admite, y para eso existe el salting o rediseñar el cálculo.
  5. Salting en dos fases. Aquí se aplica a max solo para que veas la mecánica; el detalle está en Remedios. 
    N = 16
salted = sales.withColumn("salt", (F.rand(seed=4) * N).cast("int"))
fase1 = salted.groupBy("product_id", "salt").agg(F.max("amount").alias("m"))
fase2 = fase1.groupBy("product_id").agg(F.max("m").alias("max_amount"))
fase2.count()
  6. Opcional: juega con particiones. Esta sí se puede cambiar en serverless. Repite el paso 3 con 200 y con auto, y confirma que no arregla el skew. 
    spark.conf.set("spark.sql.shuffle.partitions", "200")

Qué deberías sacar del lab: la clave caliente decide el tiempo del stage. AQE solo la parte en joins, y para ventanas o agregaciones sin parcial la solución es cambiar el algoritmo o hacer salting.
