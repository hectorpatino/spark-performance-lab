Detectar spill y skew en un stage lento

Fuentes: Diagnose cost and performance issues using the Spark UI Azure · Skew and spill Azure · Query performance insights Azure · Query history system table Azure

Lo esencial en 1 minuto

  • Orden de la guía de Databricks para el stage más largo: primero spill, después skew, después I/O, y si no es nada de eso, otras causas.
  • Spill: aparece arriba en los detalles del stage (Spill memory / Spill disk). Si no hay filas de spill, no hay spill.
  • Skew: en Summary Metrics, si Max de Duration supera en más de un 50% al percentil 75 (Max > 1.5 × p75), puede haber skew.
  • Spill solo en una o pocas tasks apunta a skew. Spill en casi todas las tasks apunta a particiones demasiado grandes para todas.
  • En serverless y SQL warehouses no hay Spark UI: usa el query profile con los insights DATA_SPILL y DATA_SKEW, y spilled_local_bytes en system.query.history.

Si solo recuerdas una cosa: antes de subir el cluster, abre el stage más largo y compara Max contra p75; con skew, más workers no ayudan.

Qué problema resuelveSaber por qué un stage tarda, antes de tocar el cluster

Un job pasa de 5 a 50 minutos. La reacción típica es subir el tamaño del cluster. La guía oficial propone otra cosa: abrir el stage más largo y revisar los sospechosos en orden fijo. Cada uno tiene un remedio distinto, y subir workers solo ayuda en algunos. Para llegar al stage más largo (Jobs Timeline, pestaña Stages) mira Leer el Spark UI.

Entra al job más largo y ordena sus stages por duración (Jobs timeline Azure, longest stage Azure). Si el stage tiene una sola task, ya tienes una pista.

Definiciones cortasSpill y skew

Spill: Spark se queda sin memoria de ejecución (la que usan shuffles, joins, sorts y agregaciones) y empieza a mover datos a disco, lo que es caro. Es más común durante el shuffle. Cómo se reparte la memoria y cuándo un spill se convierte en OOM: Memoria y OOM.

Skew: una o pocas tasks tardan mucho más que el resto. El cluster queda mal aprovechado esperando a la más lenta y el job tarda más.

ConfirmarloDe Summary Metrics a la tabla Tasks

La regla Max contra p75 te dice que algo pasa. Estas señales te dicen qué es:

  • Ordena la tabla Tasks por Duration, de mayor a menor. Si una task tardó mucho más que las demás, hay skew. Es el método de la página archivada de skew join, que también describe el síntoma típico: la query parece atascada terminando muy pocas tasks (por ejemplo, las últimas 3 de 200) (skew join Azure).
  • Mira Shuffle Read Size en Summary Metrics. Una diferencia enorme entre min y max indica que unas pocas claves concentran los datos.
  • Mira dónde está el spill. Spill solo en la task lenta apunta a skew. Spill repartido en casi todas las tasks apunta a particiones demasiado grandes para todas. Esto es una lectura del sitio a partir de las definiciones de la doc, no una regla escrita en ella.
  • Cuenta filas por clave. df.groupBy("clave").count().orderBy(F.desc("count")) sobre la clave del join o la agregación confirma el skew sin mirar ninguna UI.
  • Ajustaste las shuffle partitions y el spill sigue. Otra pista de skew: más particiones reparten las claves normales, pero la clave caliente sigue cayendo entera en una.

Las tres últimas señales vienen de la Comprehensive Guide to Optimize Data Workloads (Databricks, 2023), a la que enlaza la guía del Spark UI; no están en docs.databricks.com.

Pon el deslizador en 0% y luego súbelo poco a poco. Fíjate en tres cosas:

  • La mediana y el p75 casi no se mueven. Por eso la guía compara contra el p75 y no contra el promedio: el promedio lo arrastra la task lenta.
  • A partir de cierto punto la task caliente no cabe en memoria y aparece el spill. El tiempo crece más rápido que las filas.
  • El spill aparece solo en la task caliente. Eso apunta a skew. Si el spill estuviera repartido en casi todas las tasks, el problema sería otro: particiones demasiado grandes para todas.

En serverless y SQL warehousesLas mismas preguntas sin Spark UI

En serverless el Spark UI no está disponible; la doc indica usar el query profile (limitaciones de serverless Azure). Free Edition es serverless, así que en el lab verás el query profile, no la pantalla del stage. Las preguntas son las mismas:

PreguntaSpark UI (compute clásico)Serverless y SQL warehouses
¿Hay spill?Spill memory / Spill disk en los detalles del stageInsight DATA_SPILL en el query profile; columna spilled_local_bytes en system.query.history
¿Hay skew?Max contra p75 en Summary Metrics; tabla Tasks ordenada por DurationInsight DATA_SKEW (datos repartidos de forma desigual entre los recursos de cómputo)
¿Dónde ocurre?El stage y su nodo en SQL / DataFrameEl operador con más tiempo o Memory peak en el grafo del query profile
¿En qué queries pasa?Uno a uno en el Spark UIA escala con system.query.history, filtrando spilled_local_bytes > 0

Los insights aparecen en el panel de detalles de la query (ordenados por su efecto estimado en el tiempo total de tasks) y en la pestaña Performance insights del query profile. Cómo leer el perfil: Query profile. Queries listas para buscar spill en todas las queries: System tables.

Con qué se confundeDos trampas

  • Skew vs falta de recursos. Con skew, añadir workers no ayuda: la clave caliente sigue cayendo en una sola task. Con falta de recursos, todas las tasks son lentas por igual.
  • Spill causado por skew vs spill por pocas particiones. Si el spill viene del skew, ajustar spark.sql.shuffle.partitions no lo arregla. Primero hay que quitar el skew (ver Remedios).
