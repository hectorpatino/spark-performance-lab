Skew hints: el enfoque antiguo

Fuente: docs.databricks.com/…/archive/legacy/skew-join Azure (página archivada, puede no actualizarse)

Por qué estudiarloPara reconocerlo, no para usarlo

La página dice que los skew hints no son necesarios porque Databricks maneja el skew por defecto con AQE, siempre que spark.sql.adaptive.skewJoin.enabled sea true (el default). Lo verás en código heredado y en preguntas que buscan que elijas AQE.

SintaxisTres niveles de precisión

Cuanto más le dices, menos trabajo extra hace. La optimización de skew tiene overhead, por eso conviene acotarla.

-- 1. Solo la tabla: todos sus joins usan la optimización
SELECT /*+ SKEW('orders') */ * FROM orders, customers WHERE c_custId = o_custId

-- 2. Tabla + columna(s): solo los joins por esas columnas
SELECT /*+ SKEW('orders', 'o_custId') */ ...
SELECT /*+ SKEW('orders', ('o_custId', 'o_storeRegionId')) */ ...

-- 3. Tabla + columna(s) + valores calientes: el menor overhead
SELECT /*+ SKEW('orders', 'o_custId', 0) */ ...
SELECT /*+ SKEW('orders', 'o_custId', (0, 1, 2)) */ ...
SELECT /*+ SKEW('orders', ('o_custId', 'o_storeRegionId'), ((0, 1001), (1, 1002))) */ ...

ComparaciónHint vs AQE

Quién detectaTú, a manoSpark, con estadísticas reales del shuffle
Se adapta si cambian los datosNoSí
EstadoLegacy, página archivadaActivado por defecto
Recomendación de la docConfiar en AQE: es automático y en general rinde mejor que el hint

No confundirHints que sí siguen vigentes

El hint de broadcast sí se sigue recomendando cuando conoces la query, porque evita el shuffle desde el plan inicial (ver AQE). "Los hints son legacy" vale para SKEW(), no para todos los hints.
