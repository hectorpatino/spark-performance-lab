Azure Databricks: qué VM, spot o no, y cuánto escalar

Fuentes: Compute configuration reference, Classic compute configuration best practices, Best practices for cost optimization, Disk cache, Photon, Spark configuration, Manage classic compute, Well-Architected: Azure Databricks y Sizes for virtual machines in Azure. Las páginas de Databricks tienen equivalente en docs.databricks.com (por ejemplo Compute configuration reference), pero los detalles de VM, spot y discos de esta página son propios de Azure.

Lo esencial en 1 minuto

  • Para cargas nuevas, la doc recomienda serverless. Esta página aplica al compute clásico, donde cada nodo es una VM de Azure y Azure Databricks corre un executor por worker.
  • Memory optimized (serie E) para shuffle pesado y spill; compute optimized (F) para Structured Streaming y OPTIMIZE/VACUUM; storage optimized (L) para análisis interactivo con caché. Para ETL con joins, menos workers y más grandes.
  • Con spot, el driver siempre es on-demand, y los workers desalojados se reemplazan por spot u on-demand. Úsalo en batch que tolera retrasos, no con SLA estricto.
  • No actives spark.dynamicAllocation.enabled: no está soportado en compute clásico. Usa el autoscaling de Databricks, y evítalo en jobs de Structured Streaming.
  • Ninguna VM arregla el skew ni los archivos pequeños.

Si solo recuerdas una cosa: elige la familia según el recurso que te falta: memoria, CPU o disco local.

Qué problema resuelveEl mismo código, otra factura

Un job con spill tarda 40 minutos en una VM de propósito general y 15 en una con el doble de memoria por core. Un streaming 24/7 en spot se queda sin workers en plena tarde. Un cluster con spark.dynamicAllocation.enabled heredado de un Spark on-premise pierde nodos sin motivo. En el compute clásico de Azure Databricks, cada nodo es una VM de Azure y tú eliges su familia, si es spot y cómo escala. Esas tres decisiones pesan tanto como el código.

Antes de elegir VM: para la mayoría de cargas nuevas, la doc recomienda serverless, que no requiere configurar nada. Todo lo de esta página aplica cuando tu carga corre en compute clásico (all-purpose o job compute), porque no es compatible con serverless o porque así lo decidiste.

Un compute clásico tiene un driver y cero o más workers, cada uno en una VM de Azure. Azure Databricks corre un executor por worker, así que executor y worker son lo mismo aquí. La familia de la VM fija la proporción de CPU, memoria y disco local: memory optimized, compute optimized, storage optimized, GPU o propósito general.

Idea mentalTres recursos y un cuello de botella

Piensa cada worker como una mesa de trabajo con tres cosas: manos (cores), mesa (memoria) y un estante al lado (disco local). Si el trabajo no cabe en la mesa, los papeles van al estante y todo se vuelve lento; eso es el spill. Si el trabajo es puro cálculo, sobran mesa y estante y faltan manos. Si consultas una y otra vez los mismos papeles, conviene un estante grande y rápido cerca. Elegir familia es elegir cuál de las tres cosas compras de más.

Por dentro · 2Spot VMs: qué pasa cuando Azure las reclama

  • El driver siempre es on-demand. Con la casilla Spot instances, la primera instancia es on-demand y las siguientes son spot. La doc de costos lo recomienda así: el driver nunca en spot. Tampoco uses un pool de spot como tipo de driver.
  • Eviction. Si Azure desaloja workers, Databricks intenta conseguir spot nuevas. Si no hay, pone on-demand en su lugar. Ese reemplazo solo cubre spot que ya estaban adquiridas y corriendo: las que fallan durante el arranque no se reemplazan solas.
  • Al escalar, los nodos nuevos también se piden como spot.
  • Cuándo sí: la doc recomienda spot para cargas con requisitos de latencia laxos, donde es aceptable tardar más porque se perdió algún worker.
  • En la API (azure_attributes): first_on_demand fija cuántos nodos iniciales son on-demand; availability acepta SPOT_AZURE, ON_DEMAND_AZURE o SPOT_WITH_FALLBACK_AZURE; spot_bid_max_price = -1 significa que la VM no se desaloja por precio (solo por capacidad): pagas el precio spot del momento, como mucho el de una VM estándar (Azure Spot VMs · Eviction policy; Bundle resources · instance_pool Azure).
  • Capacity reservation groups garantizan capacidad de un tamaño de VM, pero exigen on-demand y un workspace con VNet propia. No se combinan con spot.

Por dentro · 4Disk cache y Photon

  • Disk cache (antes Delta cache o DBIO cache) copia los archivos Parquet remotos al disco local de los workers en un formato intermedio rápido, en la primera lectura. Funciona con tablas Delta en ABFS. La forma recomendada de usarlo es elegir un tipo de worker con volúmenes SSD: esos vienen activados y configurados, y la caché usa como mucho la mitad del SSD local. Se controla con spark.databricks.io.cache.enabled.
  • Disk cache y Spark cache son distintos. El disk cache es automático, vive en archivos locales y se invalida solo cuando cambian los archivos. cache()/persist() es manual y guarda bloques en memoria. En SQL warehouses y DBR 14.2+, CACHE SELECT se ignora.
  • Photon viene activado por defecto en all-purpose y job compute (casilla Use Photon Acceleration). Por API hay que pedirlo con runtime_engine = PHOTON. Las instancias con Photon consumen DBU a otra tarifa. Ayuda más en joins, agregaciones y scans grandes; no mejora queries de menos de dos segundos, no soporta UDF ni RDD, y en streaming solo cubre consultas stateless. Predictive I/O y dynamic file pruning en MERGE/UPDATE/DELETE lo requieren.
Verifica: que la serie L sea la mejor opción para disk cache es una deducción. La doc de Databricks dice "worker con volúmenes SSD" y "storage optimized" para caché; la doc de Azure dice que la serie L trae NVMe local. No encontré una página de Databricks que nombre la serie L para disk cache. Revisa en el desplegable de tu workspace qué tipos aparecen como acelerados para caché.

Monitoreo en AzureMétricas fuera de Databricks

  • Pestaña Metrics del compute: métricas de hardware cada minuto en all-purpose y job compute (CPU, memoria, swap, disco libre, red, nodos activos). La misma información a nivel de nodo está en system.compute.node_timeline (90 días).
  • Azure Monitor: puedes configurar el compute para que envíe métricas a un Log Analytics workspace. Si tu workspace usa VNet propia con NSG que niegan la salida, necesitas una regla de salida para el service tag AzureMonitor. En bundles, azure_attributes.log_analytics_info tiene log_analytics_workspace_id y log_analytics_primary_key.
  • Logs de diagnóstico: la guía Well-Architected recomienda enviar los logs de diagnóstico del workspace (clusters, jobs, notebooks, Unity Catalog…) a Log Analytics y montar alertas de Azure Monitor sobre ellos.
  • Costo en Azure: los tags del compute llegan a las VM, a los discos y a los logs de uso de Databricks, y se pueden analizar en Azure Cost Management. En compute que sale de un pool, los tags personalizados solo van a los reportes de DBU.
Verifica el procedimiento exacto para enviar métricas de compute a Log Analytics. La página de Databricks dice que es posible y menciona la regla de NSG, pero no trae los pasos.

Cómo se usaUn job compute con spot y fallback

Job compute para un ETL con joins grandes que puede tardar algo más si pierde workers. Memory optimized, autoscaling, driver on-demand y workers spot con fallback a on-demand (Clusters API):

{
  "spark_version": "<versión LTS más reciente>",
  "node_type_id": "Standard_E16ds_v5",
  "driver_node_type_id": "Standard_E16ds_v5",
  "autoscale": { "min_workers": 2, "max_workers": 8 },
  "runtime_engine": "PHOTON",
  "azure_attributes": {
    "first_on_demand": 1,
    "availability": "SPOT_WITH_FALLBACK_AZURE",
    "spot_bid_max_price": -1
  }
}

Lo que no lleva: spark.dynamicAllocation.* ni spark.executor.memory. La doc pide no fijar configuraciones de Spark en la definición del compute, porque anulan optimizaciones que Databricks ya trae.

Verifica que Standard_E16ds_v5 esté disponible en tu región y en el desplegable de tu workspace. El nombre sigue la serie Edsv5 de la doc de Azure, pero la lista de tipos soportados depende de cada workspace.

Cuándo usarloY cuándo no

  • Serverless primero. Si la carga es compatible, no eliges VM ni spot.
  • SQL interactivo: un SQL warehouse es el motor más eficiente en costo según la doc; no armes un all-purpose para eso.
  • Jobs en job compute, no en all-purpose: cuestan bastante menos y cada job puede tener su propio compute.
  • Spot sí en batch que tolera retrasos. Spot no cuando el SLA es estricto, ni para el driver.
  • Un analista solo: la doc sugiere single node con una VM grande, storage optimized con disk cache.
  • Pools: reducen el arranque y el tiempo de escalado. No cobran DBU por instancias ociosas, pero Azure sí cobra las VM.

Con qué se confunde

  • Autoscaling de Databricks y dynamic allocation de Spark. El primero agrega y quita VMs y gestiona los executors; el segundo no está soportado en compute clásico de Databricks.
  • Autoscaling local storage y disk cache. El primero agrega managed disks cuando falta espacio (útil para spill). El segundo usa el SSD local para cachear Parquet. Un disco grande no convierte una VM en acelerada para caché.
  • Spot con fallback y capacity reservation. El fallback cambia spot por on-demand si no hay spot. La reserva asegura capacidad de un tamaño concreto y solo funciona con on-demand.
  • Photon y serverless. Photon es el motor de ejecución; también existe en compute clásico. Serverless es quién administra las VM.

Qué pasaría si

  • Pones el driver en un pool de spot: si Azure lo reclama, pierdes la sesión entera. La doc lo desaconseja.
  • Mantienes spark.dynamicAllocation.enabled=true de una migración: riesgo de NODES_LOST y tasks que no arrancan. Quítalo y usa min/max workers.
  • Subes de 4 a 16 workers para un stage con skew: pagas cuatro veces más y la task caliente sigue sola.
  • Corres VACUUM de una tabla enorme con muchos workers pequeños: la fase de borrado ocurre solo en el driver. La doc sugiere 1 a 4 workers de 8 cores y un driver de 8 a 32 cores, más grande si hay OOM.
  • Una spot falla al arrancar: no se reemplaza sola. Y si Azure termina instancias, el compute puede quedar por debajo del mínimo de workers mientras Databricks reintenta aprovisionarlas.
