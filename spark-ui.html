Leer el Spark UI

Fuentes: Apache Spark · Web UI · Debugging with the Spark UI Azure · Diagnose cost and performance issues using the Spark UI Azure · Manage classic compute Azure · Failing jobs or executors removed Azure · Spark memory issues Azure · Compute log delivery Azure

Lo esencial en 1 minuto

  • El Spark UI solo existe en compute clásico. En serverless y en SQL warehouses usas el query profile, que muestra operadores y no tasks.
  • Ruta de la guía de Databricks: Jobs → Event Timeline, luego el stage más largo, luego spill y skew (Max de Duration más de un 50% por encima del p75), luego I/O y otras causas.
  • Ordena jobs, stages y tasks por duración. La task caliente sale arriba, y más workers no la aceleran porque una partición la ejecuta un solo core.
  • exited caused by one of the running tasks apunta a memoria. exited unrelated to the running tasks apunta a una máquina perdida: confírmalo en el Event log del compute.
  • Un job en SUCCEEDED puede traer tasks fallidas y stages repetidos (FetchFailed, (retry 1)). Si reinicias el compute, pierdes su Spark UI.

Si solo recuerdas una cosa: mira el Spark UI antes de tocar el cluster, y en el stage más largo compara Max con p75.

Qué problema resuelveEncontrar la causa antes de tocar el cluster

El Spark UI te deja bajar del job a la task para saber qué falla antes de pagar más cluster.

Un job en compute clásico pasa de 3 a 12 minutos, o termina bien pero con tasks fallidas. Desde el notebook solo ves el tiempo total. El Spark UI te deja bajar del job al stage, del stage a la task y de la task al executor donde corrió. Con eso distingues skew, spill, falta de paralelismo, I/O alto o un executor perdido, y cada uno tiene un remedio distinto.

La sección 9 del examen pide justo esto: identificar la información de diagnóstico útil en el Spark UI, los logs del cluster, las system tables y el query profile.

Definición cortaQué es el Spark UI

El Spark UI es la interfaz web de la aplicación Spark que corre en un compute clásico. Muestra los jobs, stages y tasks, el almacenamiento en caché, la configuración, los executors y las queries SQL de esa aplicación.

En Databricks hay un Spark UI por compute. Si reinicias un compute terminado, el Spark UI muestra la información del compute reiniciado, no la historia del anterior (Manage classic compute Azure).

Idea mentalUn zoom de cuatro niveles

Piensa en un mapa con zoom. La aplicación es el país: en el Event Timeline ves todos los jobs y cuándo entran o salen executors. El job es una ciudad: sus stages y cuánto leyó, escribió y movió cada uno. El stage es un barrio: las Summary Metrics te dicen si todas las tasks se parecen o si una se sale. La task es la calle: en qué executor corrió, cuánto leyó y por qué falló. Las pestañas Executors y SQL / DataFrame son dos vistas laterales del mismo mapa: quién hizo el trabajo y qué plan se ejecutó.

Cómo se usaAbrirlo en Databricks

En compute clásico está en Compute → tu compute → Spark UI. En serverless no existe.

  1. Compute clásico. Ve a Compute, elige tu compute y haz clic en la pestaña Spark UI (How to open the Spark UI Azure).
  2. Un job de Lakeflow en compute clásico. La guía de rendimiento de jobs dice que para compute clásico uses el Spark UI: primero el Event Timeline para ver jobs largos, huecos o fallos, y luego los stages y tasks (Diagnose Lakeflow Jobs performance Azure). El panel de cada task muestra el cluster que la ejecutó y enlaces a sus logs.
  3. Serverless. No hay Spark UI. En notebooks y jobs serverless se usan las query insights y el query profile, que muestran operadores, no tasks (Serverless limitations Azure). Free Edition es serverless.
Verifícalo en tu workspace: la doc de jobs no dice con qué nombre aparece el enlace al Spark UI dentro del panel de la task. Lo confirmado es la ruta Compute → tu compute → Spark UI.

SimuladorSpark UI navegable

Practica la ruta completa en una aplicación con dos problemas a la vez.

Una aplicación inventada en un compute clásico de Azure: 4 workers spot de 8 cores, driver on-demand y sin autoscaling. El notebook hace clientes.join(ventas, "cliente_id", "left").write.saveAsTable(...) y tardó mucho más de lo normal. Navega como en la herramienta real: pestañas arriba, enlaces en las descripciones, Event Timeline y Show Additional Metrics se despliegan, y los encabezados en azul ordenan la tabla. Las celdas con subrayado punteado rojo son evidencias: haz clic para inspeccionarlas.

Spark UI de la aplicación · datos ilustrativos

Haz clic en una celda subrayada para ver qué significa. Empieza por Jobs → Event Timeline.

Pistas

    ¿Cuál es el diagnóstico?

    Qué harías ahora. Para el skew: trata aparte la clave cliente_id = 0 (filtrarla, procesarla en otro paso o hacer salting), o cambia el join para que ventas quede en el lado que AQE sí puede partir, si la lógica lo permite. Ver Remedios y AQE. Para el executor perdido: confirma en el Event log del compute que fue una VM spot reclamada, y valora decommissioning o workers on-demand para este job (sección de errores, más abajo).

    Subir workers no habría ayudado con la task caliente: una partición la ejecuta un solo core.

    Qué observar mientras navegas:

    • En el Event Timeline de Jobs hay un job que ocupa casi todo el eje y un executor en rojo. Son dos problemas distintos que conviven en la misma aplicación.
    • En el Stage 4, la tabla de tasks ordenada por Index parece normal. Ordénala por Duration y la task caliente sale arriba. La guía de Databricks propone lo mismo con los jobs y los stages: ordenar por duración.
    • En el Event Timeline del stage, todas las tasks terminan en el primer tramo y una sola barra cruza el resto del eje.
    • El executor 3 murió durante el Job 2. El Job 2 terminó bien, pero con tasks fallidas que Spark repitió.

    Cómo se usaLa ruta de diagnóstico de Databricks

    La guía oficial dice qué mirar y en qué orden. El paso del stage (spill y skew) está a fondo en Diagnóstico. Aquí tienes dónde está cada paso en el Spark UI (Spark UI guide Azure).

    1

    Jobs timeline. Jobs → Event Timeline. Busca jobs o executors en rojo (Failing jobs or executors removed Azure), huecos de un minuto o más, uno o pocos jobs largos, o un timeline lleno de jobs diminutos. Si no ves nada, ordena los jobs por duración y abre el más largo. Ojo: un job figura como running desde que se envía, no desde que empieza su primera task (Jobs timeline Azure).

    2

    El stage más largo. En la página del job, ordena los stages por duración y anota Input, Output, Shuffle Read y Shuffle Write. Un stage con una sola task puede ser señal de problema (Look at longest stage Azure).

    3

    Spill o skew. Spill arriba en los detalles del stage; skew en Summary Metrics, comparando Max con p75 de Duration (Skew and spill Azure). Lo practicas en Diagnóstico.

    4

    ¿I/O alto? Divide la columna de I/O más grande entre los cores de los workers y luego entre los segundos del stage. Si sale alrededor de 3 MB por segundo, probablemente el stage está limitado por I/O (Spark stage high I/O Azure).

    5

    Otras causas. Con poco I/O, abre el DAG SQL (Associated SQL Query) y busca muchos archivos pequeños leídos o escritos (decenas de miles, de menos de 8 MB), UDFs lentas, un cartesian join o un join que explota filas (Slow Spark stage with little I/O Azure).

    Cómo se usaErrores que conviene reconocer

    Lee el texto exacto: dice si el executor murió por una de sus tasks o por algo ajeno, y eso cambia dónde buscas.

    Estos textos aparecen en la columna Errors de la tabla de tasks, en el motivo de fallo de un stage o en los driver logs. Los formatos de ExecutorLostFailure, FetchFailed y Resubmitted salen del código de Apache Spark (TaskEndReason.scala); el ejemplo completo de memoria es de la guía de Databricks.

    Lo que vesQué suele significarDónde confirmarlo
    ExecutorLostFailure (executor 4 exited caused by one of the running tasks) Reason: Remote RPC client disassociated. Likely due to containers exceeding thresholds, or network issues.El executor murió y Spark cree que lo causó una de sus tasks. La guía de Databricks lo pone como ejemplo típico de problema de memoria, pero avisa de que el mensaje es genérico.Prueba a duplicar la memoria por core (mismo número de cores, el doble de RAM). Si tarda más en fallar o deja de fallar, vas bien. Causas habituales: pocas particiones de shuffle, broadcast grande, UDFs, ventana sin PARTITION BY, skew, estado de streaming. Ver Memoria y OOM.
    ExecutorLostFailure (executor 3 exited unrelated to the running tasks)El executor desapareció por algo ajeno a la task: por ejemplo, la máquina dejó de existir.Compute → Event log: busca cambios de tamaño o pérdida de instancias spot.     Workers spot en Azure

    La guía de Databricks da tres causas comunes de executors retirados: autoscaling (esperado), pérdida de instancias spot y executors sin memoria. En Azure, una Spot VM se desaloja cuando Azure necesita la capacidad (o cuando el precio supera tu máximo). Azure envía el evento de desalojo (Scheduled Events) hasta 30 segundos antes, con mejor esfuerzo (Azure Spot VMs · Eviction policy). Si pierdes spot con frecuencia, la guía sugiere mirar el historial de desalojos de cada tipo de instancia o dejar de usar spot (Losing spot instances Azure).

    • Driver on-demand y reemplazo. El driver no debe ser spot, y Azure Databricks reemplaza las spot desalojadas por otras spot u on-demand. Los detalles y los campos de azure_attributes están en Azure.
    • Decommissioning. Aprovecha el aviso previo para migrar los bloques de shuffle y de caché (RDD) a executors sanos. Necesita las propiedades del bloque siguiente en Spark config y una variable en Environment variables; la de caché no se recomienda si tu StorageLevel ya replica más de una vez. Con decommissioning activado, los fallos de tasks por desalojo no cuentan como intentos fallidos. Es de mejor esfuerzo: no garantiza evitar los fetch failures (Decommission spot instances Azure).
    # Spark config del compute (Advanced → Spark)
spark.decommission.enabled true
spark.storage.decommission.enabled true
spark.storage.decommission.shuffleBlocks.enabled true
spark.storage.decommission.rddBlocks.enabled true

# Environment variables (mismo panel): decommissioning de los workers
SPARK_WORKER_OPTS="-Dspark.decommission.enabled=true"

    Cuándo usarlo y cuándo noSpark UI, query profile o logs

    Elige la herramienta según el compute y la pregunta.

    • Spark UI: compute clásico (all-purpose y jobs). Es la única vista con tasks, executors y la tabla de tasks fallidas.
    • Query profile: serverless (notebooks y jobs) y SQL warehouses. Muestra operadores y métricas por operador, no tasks.
    • Event log y driver logs: cuando la pregunta es por qué se perdió una máquina, por qué no arrancó el compute o qué excepción lanzó el driver.
    • System tables y entrega de logs: cuando necesitas la historia después de reiniciar el compute, o comparar muchos compute a la vez.

    Con qué se confundeCinco trampas

    Cinco lecturas del Spark UI que llevan a conclusiones equivocadas.

    • Executor retirado no siempre es un error. Con autoscaling, ver executors removidos es lo esperado. Confírmalo en el Event log antes de culpar a la memoria.
    • Event Timeline de Jobs y Event Timeline del stage. El primero muestra jobs (o stages, en la página del job) y executors. El segundo muestra cada task partida en 7 fases: Scheduler Delay, Task Deserialization Time, Shuffle Read Time, Executor Computing Time, Shuffle Write Time, Result Serialization Time y Getting Result Time.
    • Task Time en Executors frente a duración del stage. Task Time suma la duración de todas las tasks del executor. Un executor con mucho Task Time puede ser solo el que recibió la task caliente.
    • Tiempos del DAG SQL frente a tiempo de reloj. Los tiempos de los operadores son acumulados. Sirven para comparar operadores entre sí, no para sumar minutos de espera.
    • Job terminado no significa job sano. Spark reintenta tasks; un job puede acabar en SUCCEEDED con tasks fallidas y minutos perdidos repitiendo trabajo.

    Qué pasaría si

    Decisiones habituales y lo que provocan en el Spark UI.

    • Reinicias el compute para limpiar antes de mirar: pierdes el Spark UI de la ejecución que querías estudiar. Mira primero, o configura la entrega de logs.
    • Mueves el mismo notebook a serverless: ya no hay Spark UI. Las mismas preguntas se responden en el query profile, con operadores en vez de stages.
    • Subes de 4 a 8 workers con la task caliente del simulador: el Stage 4 sigue esperando a una sola task. Pagas el doble de cores mirando.
    • Activas decommissioning en el cluster spot: cuando Azure avise del desalojo, Spark intentará migrar los bloques de shuffle (y los de caché, si activaste rddBlocks). Menos tasks repetidas, aunque sin garantía.
